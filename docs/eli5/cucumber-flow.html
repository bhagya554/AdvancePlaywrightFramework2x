How a Cucumber scenario runs

One config file picks which .feature files to read, then every scenario gets its own fresh box — the World — to carry the browser and the page objects.

What happens, step by step

  1. You run cucumber-js

    A profile flag picks one slice of the suite — level0, level1, level2.

  2. cucumber.js answers two questions

    Which .feature files to read, and which step files to load.

  3. ts-node makes TypeScript runnable

    It compiles on the fly; tsconfig-paths teaches it @pages/*.

  4. world.ts registers the World class

    setWorldConstructor(CustomWorld) — use mine, not Cucumber's default.

  5. Each scenario gets a fresh World

    Built empty. Every field is still undefined at this moment.

  6. The Before hook fills it in

    Launch browser, open a page, call initPages(). This is the missing piece.

  7. Steps share that one object

    this.page, this.loginPage, this.scratch — same instance throughout.

⚠️ The part that surprises people

Every field in CustomWorld is declared with ! — browser!, page!, loginPage! (src/cucumber/support/world.ts:24). That tells TypeScript "I promise this gets assigned later", and the promise is kept by the Before hook.

But src/cucumber/support/hooks.ts is 0 bytes. Nothing launches a browser and initPages() is never called, so npm run typecheck passes cleanly while the first scenario dies on this.page being undefined. The ! moved the error from compile time to run time.

Try it

npx cucumber-js -p level1

Right now this finds no .feature files, because src/cucumber/level-01-basic/ does not exist yet — cucumber.js names the folders the suite is meant to grow into.
